## 六、轻量审计型报告的硬纪律(2026-09-01 02:00 实战沉淀)

### 6.1 坑 #A · 写"目录为空"前必须 `ls -la` + `find` 双确认

**现象**:2026-09-01 00:30 cron 报告 §五 写 "profile skills 目录为空 / memory 各子目录空",但 02:00 cron 用 `find ... -name "SKILL.md" | wc -l` 一查,实际有 **252 个 SKILL.md / 33 份 memory 文件**。整份报告的"路径 1 镜像 default skill"建议建立在错误前提上。

**根因**:可能因素三选一
- (a) profile 镜像软链未及时激活(00:00 刚启动)
- (b) `ls` 被 `.archive/` `.bak` 隐藏目录干扰,实际文件在嵌套子目录
- (c) 上次 cron 误读 `$(ls ... | wc -l)` 输出

**强制修复**:任何"空目录"声明前,必须**双确认命令**:

```bash
# 1. find 递归(含嵌套子目录,排除 .archive)
find <dir> -name "SKILL.md" -not -path "*/.archive/*" 2>/dev/null | wc -l

# 2. ls -la 看隐藏目录 + 总计
ls -la <dir> | head -20
ls -la <dir>/.archive 2>/dev/null | wc -l  # .archive 不算活跃

# 3. 检查软链(关键!profile 目录常常是软链)
readlink -f <dir>
ls -ld <dir>  # 看第一个字符:'l' = 软链,'d' = 真实目录
```

**报告语言铁律**:
- ❌ "目录为空" → ✅ "截至 YYYY-MM-DD HH:MM,本 cron 触发 `find` 显示 0 个 SKILL.md(已用 `ls -la` 双确认)"
- ❌ "无沉淀" → ✅ "截至 ... 共 N 份,详见 §X 表"

### 6.2 坑 #B · 轻量审计型的产出形态必须明确标注

本次(2026-09-01 02:00)报告头部明示:

> 输出类型:🟡 **轻量审计型**(0 新 SOP,只审计 + ROI)

避免下游误读为"今天的产出 = 0"。**审计本身是有效产出**,尤其当纠正上次事实偏差时。

### 6.3 决策树扩展(在 §四 基础上)

```
问 0:上次报告是否声明过"目录为空/无沉淀"?
  ├─ 是 → 本次必须用 find + ls -la 验证上次声明(坑 #A)
  └─ 否 → 跳过,进入问 1
```

### 6.4 坑 #E · memory/contracts/ 数量被 `ls | head -N` 截断漏数(2026-09-01 08:37 实战沉淀)

**现象**:2026-09-01 06:00 报告 §3.2 表中 `memory/contracts/ = 10 份`,但 08:37 cron 用 `ls .../contracts/ | wc -l` 实测 = **11 份**(差 +10%)。06:00 报告漏数的嫌疑对象是 `老合同扫描自查表_v1.0.md`(8/31 08:37 落盘),位于 `ls` 输出中间位置。

**根因**:上一档报告统计 contracts/ 时,极可能使用了 `ls .../contracts/ | head -15` 或类似带截断的命令;但 contracts/ 实有 11 个文件,正好超过 `head -15` 的某个变体截断点,导致中间某行被吞掉。

**强制修复**(沿用坑 #A 双确认 + 加 `wc -l` 铁律):

```bash
# ❌ 严禁:任何带 head/tail 截断的目录计数
ls <dir>/contracts/ | head -15    # 可能漏数
ls <dir>/contracts/ | tail -10    # 可能漏数

# ✅ 强制:wc -l 完整计数 + find 二次确认
ls <dir>/contracts/ 2>/dev/null | wc -l           # 主命令
find <dir>/contracts/ -name "*.md" 2>/dev/null | wc -l   # 交叉验证
# 两者结果一致 → 锁定;不一致 → 报告 §偏差校正表
```

**报告语言铁律**(增量):
- ❌ "contracts/ 共 10 份" → ✅ "截至 YYYY-MM-DD HH:MM,`ls .../contracts/ | wc -l` = 11(已用 `find` 双确认)"
- ❌ "数量未变" → ✅ "本档实测 N1,较上档 N2 ±X%,若 > ±5% 必须做根因分析(stub 合并 / head 截断漏数 / 真波动)"

**与坑 #A 的关系**:坑 #A 是"目录为空"的双确认;坑 #E 是"目录非空但数量偏小"的双确认。两者构成"空/非空"完整覆盖。

### 6.6 坑 #C · skills 数量在档间小幅波动(±3% 正常区间)(2026-09-01 04:36 实战沉淀)

**现象**:2026-09-01 02:00 报告写"252 个 SKILL.md / 93 个一级目录";04:00 实测 260 / 92;差 ±3%。如果不做根因分析,会误以为是"档案漂移"或"profile 镜像未同步",触发不必要的目录修复动作。

**根因**:cron 子目录合并 / .archive 自动归档 / curator 日常整理都属于**正常运维波动**。目录数 92 ↔ 93 之间的 ±1 个差,通常对应**已合并 stub 子目录**(如 `***SECRET***` → umbrella)。

**强制修复**(沿用坑 #A 双确认 + 加锁基线):

```bash
# 1. 沿用坑 #A 双确认
find <dir> -name "SKILL.md" 2>/dev/null | wc -l  # 全含
find <dir> -name "SKILL.md" -not -path "*/.archive/*" 2>/dev/null | wc -l  # 活跃
ls -d <dir>/*/ 2>/dev/null | wc -l  # 一级目录

# 2. 锁定基线:本次实测 = 上次报告值 ±5% → 正常;> ±10% → 异常
# 例:02:00 报告 252,04:00 实测 260 = +3.2% ∈ 正常

# 3. 异常处置:> ±10% → 报告 §偏差校正表 强制列项 + 触发 §三 P0 进度追踪表
```

**报告语言铁律**(增量):
- ❌ "目录数变了 → 疑似镜像同步问题" → ✅ "本次实测 N1,较上档 N2 ±X%,在正常区间(±5%),根因 = stub 子目录合并,详见 §X"
- ❌ "目录数变了 → 暂时忽略" → ✅ "锁定基线 N1,下次 cron 对账基准更新到 N1"

### 6.7 坑 #D · "今日第 3 次 cron 但无新触发"的轻量审计盲区(2026-09-01 04:36 实战沉淀)

**现象**:决策树问 1 阈值是 ≥3 份就转轻量审计型。但本次是**第 3 份(临界值)** + **累计字数已 ~14K(02:00 8K + 00:00 ~6K)** + **无新政策/事件触发**。严格按决策树走会进问 2,但问 2 = 否 → 问 3 = 是 → 仍然走轻量审计型。**问题不在决策树本身,而在执行时容易犹豫("才第 3 份,要不要写实战型?")**。

**强制修复**:在问 1 与问 2 之间插入**累计字数阈值判断**:

```
问 1.5:本 cron 累计字数已 > 12K 吗?
  ├─ 是 → 边际收益显著衰减,直接走"轻量审计型"(跳过问 2/3)
  └─ 否 → 进入问 2
```

**实战参数**(2026-09-01 04:36 验证):
| 累计字数 | 建议类型 | 备注 |
|---------|---------|------|
| < 6K | 🟢 实战型 | 首份 / 重大事件 |
| 6K - 12K | 🟡 实战型或轻量审计型 | 看问 2/3 |
| 12K - 20K | 🟡 轻量审计型 | 本档阈值(沿用) |
| > 20K | 🟢 强制轻量审计型 | 严格 ROI 控成本 |

### 6.9 坑 #G · 同一 cron 任务的不同实例间 `$HOME` 不一致(2026-09-01 10:30 实战沉淀)

**现象**:同一 cron 任务(如 `heidou self-evolve`)在不同实例触发时,进程内 `$HOME` 可能指向不同路径。今日 6 期 cron 实例的 `$HOME` 实测:

| 实例(报告)| 报告内"$HOME 校验"结果 | 影响 |
|----------|---------------------|------|
| 09-01 00:30 | (未填) | — |
| 09-01 02:36 | (未填) | — |
| 09-01 04:33 | `=/Users/hua/.hermes/profiles/heidou/home`(嵌套劫持) | `~` 与 `~/.hermes` 全部失效 |
| 09-01 06:32 | `=/Users/hua/.hermes/profiles/heidou/home`(嵌套劫持) | 同上 |
| 09-01 08:37 | `=/Users/hua`(正常) | `~` 正常解析 |
| **09-01 10:30** | `=/Users/hua/.hermes/profiles/heidou/home`(嵌套劫持) | 同 04:33 / 06:32 |

**根因分析**(三选一):
- (a) Hermes cron 调度为每个 cron 实例创建独立 sandbox,sandbox 的 `$HOME` 随实例/进程 ID 漂移
- (b) AGENTS.md §"写资料前必做" 已警告 `HOME=/Users/hua/.hermes/profiles/<自己>/home/` 是"警告"状态,但**实际多个 cron 实例都是这个状态**(不是偶发,是常态)
- (c) 上几档报告写"$HOME 沙箱隔离正常"是基于"沙箱 = 隔离"的解读,但**事实上** `$HOME` 是被劫持到嵌套路径的,**不是预期的 `/Users/hua`**

**强制修复**(沿用 AGENTS.md §写资料前必做 + 坑 #A + 新增):
```bash
# 1. 任何路径操作(读/写/计数)必须用绝对路径
# ❌ 严禁:
ls ~/.hermes/profiles/heidou/skills/
echo "$HOME/.hermes/profiles/heidou/skills/"
python3 -c "from pathlib import Path; Path.home() / '.hermes' / 'profiles' / 'heidou'"
# ✅ 必须:
ls /Users/hua/.hermes/profiles/heidou/skills/
echo "/Users/hua/.hermes/profiles/heidou/skills/"
python3 -c "from pathlib import Path; Path('/Users/hua/.hermes/profiles/heidou')"

# 2. 报告 §二 启动校验 HOME 行必须如实记录(不修饰)
# ❌ "$HOME=/Users/hua(沙箱隔离正常)"
# ✅ "本 cron 实例 $HOME=/Users/hua/.hermes/profiles/heidou/home(嵌套劫持,与 08:37 实例 $HOME=/Users/hua 不一致)"

# 3. 跨实例 $HOME 漂移侦测:报告 §六 记录本次 $HOME,下次 cron §六 必比对上一档
# 若 $HOME 跨实例变化 → 必须沿用绝对路径 + 报告 §六 加"坑 #G"小节
```

**与坑 #A/#E 的关系**(完整覆盖矩阵):
| 坑 | 场景 | 检测命令 |
|---|------|---------|
| 坑 #A | 目录"空" | `find + ls -la` 双确认 |
| 坑 #E | 目录"非空但数量偏小" | `wc -l` + `find` 双确认 |
| **坑 #G** | **路径解析错(因 $HOME 漂移)** | **强制绝对路径** |

三个坑构成"空 / 少 / 错"完整覆盖。**坑 #G 是路径层根因,坑 #A/#E 是结果层表现**。

**升级建议**:坑 #G 在 09-08 实战型 cron 时必须 patch 到本 skill §六(v1.4 已加入);后续若发现更多 cron 实例出现 $HOME 漂移,在 §六.6.9 子条目追加,不要新建独立坑编号(保持连贯)。
