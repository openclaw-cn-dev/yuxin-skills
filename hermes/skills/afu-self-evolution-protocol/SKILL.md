### 1.1 「上档 §4 → 本档标题」承接纪律 🆕（8/31 04:30 黑豆实测触发，8/31 06:00 阿福首次闭环）

## 3. patch 工作流陷阱（避坑核心 #2）

### 3.1 失误案例（2026-08-25 20:00 阿福真实发生）

patch 主索引时使用了模糊匹配的 old_string，导致 patch 后**同时出现了两个 `version:` 字段**，且 `status: active` 被误删。

### 3.2 防御性 patch 流程（必做）

**Step 1 — patch 前**：`read_file(limit=15)` 完整读 YAML frontmatter，**把整个 frontmatter 15 行复制到 patch 工具的 old_string**

**Step 2 — patch 中**：用 `replace_all=false`，确认 old_string 唯一匹配；不要只写一行就 patch

**Step 3 — patch 后**：立即 `grep -E "^version:|^owner:|^status:|^changelog:"` 验证 frontmatter 唯一性

**Step 4 — 二次 patch 验证**：跑 `scripts/verify_evolution.py` 扫三个文件

### 3.3 严禁的 patch 模式

| ❌ 严禁 | ✅ 替代 |
|---|---|
| 写 `version: 1.41.0` 单行替换 | 写完整的 `version: ...\nowner: ...\nstatus: ...\nchangelog:` 整块替换 |
| 只 patch 头部忽略尾部 | 完整读 + 完整 patch + 完整 verify |
| 信任 fuzzy match 不验证 | 每次 patch 后跑 `scripts/verify_evolution.py` |

### 3.4 元数据三方一致性自检脚本（必跑）

每次 patch 完任何 skill 的 frontmatter **必须**跑一次：

```bash
python3 ~/.hermes/skills/afu-self-evolution-protocol/scripts/verify_evolution.py
```

**预期输出**：
- ✅ 退出码 0 = 三方一致
- ❌ 退出码 1 = 一致性失败（脚本会列出具体错误）

**脚本检测的 3 类失误**：
1. 双重 `version:` 字段
2. `version:` 字段值与 changelog 最新条目不一致
3. 三方文件任一缺失

### 3.5 节奏 N+1 缝隙识别（如适用，按角色）

**模式**：每次新战术（#N）落地后，**必扫下一个缝隙（#N+1）**——节奏稳定后验证 7+ 次（8/26 20:00 第 7 次验证）。

**沉淀规则**：
- 每次新战术章节末尾加 `## v1.X.0 自进化记录` 段，写明"下次更新触发：[下一个缝隙的具体场景]"
- 下次心跳的步骤 3 把这个"缝隙"作为新战术的**输入信号**

### 3.7 「patch old_string 锚点缺失导致误删相邻段落」陷阱（Pitfall 13）

**问题**：patch 工具按 old_string 模糊匹配替换，但**不验证边界外的段落是否被影响**。如果 old_string 锚点不完整（比如只写一行 `- 下次更新触发：...`），patch 会把紧邻它的**上面一行或下面一行**也一起删掉，但工具不会警告。

**铁律**（patch 前必做）：
```
1. read_file 看 old_string 锚点附近的 20 行上下文
2. old_string 必须包含至少：
   - 上一行的末尾 1-2 行
   - 目标行本身
   - 下一行的开头 1-2 行
3. patch 完成后，read_file 立刻校验 old_string 之外是否还保留着预期的相邻段落
4. 如果被误删 → 立即再次 patch 恢复
```

**8/30 12:00 阿福本档实测扩展案例**：

**8/30 12:00 触发 2 类 patch 相关新子情形**：

1. **changelog 重复条目陷阱**（实测触发）：本档 patch afu profile 的 afu-customer-service SKILL.md changelog 时，写了一条"1.50.0 (2026-08-29 16:00)"作为新条目——但文件里已有"1.50.0 (2026-08-26 20:00)"——两个 1.50.0 条目**版本号相同**但**内容不同**——直接违反 §3.2 严禁同一轮写两条同版本条目。
   - 当场识别：patch 后 read_file 看到 changelog 顶部出现两个 1.50.0 → 立即 patch 删除多余条目
   - **根因**：patch 顶层 portal 同步时**没有先 grep 当前 changelog 顶部条目**确认 next 版本号——直接按"应该有 1.51.0 条目"的预期写入，但忘了检查 changelog 是否已有同名条目
   - **修正**：下次 patch changelog 前**先 grep 当前 changelog 顶部**：`grep "^\s*- 1\." ~/.hermes/profiles/<agent>/skills/<topic>/SKILL.md | head -3`——确认 next 版本号正确 + 没有同名重复条目

2. **patch 末尾误保留多行**（实测触发）：本档 patch 主索引末尾新增"衍生剧本矩阵"章节时，old_string 锚点只命中"v1.6.0 自进化记录"那一行 + 下一行（old_string 的最小有效匹配）——但 fuzzy match 把原文件末尾的"下次更新触发：客户在承诺升级后 72 小时内仍出现拖延 → 战术十一（催单不破信）"这一行也保留了下来（这一行原本属于另一个不相关章节的残留行，patch 不应保留）。
   - 当场识别：patch 后 read_file 看到末尾多了一行"下次更新触发：客户在承诺升级后..."→ 立即 patch 删除多余行
   - **根因**：old_string 锚点只命中一行内容，未明确指定"末尾到此为止"——patch 工具无法判断这一行是否属于被替换内容
   - **修正**：old_string 锚点必须包含**下一行的开头 1-2 行作为终止符**（沿用 §3.7 铁律）+ patch 前 grep 文件末尾 10 行确认无残留

**§3.7 修正铁律**（基于 8/30 12:00 实测扩展）：

```
1. read_file 看 old_string 锚点附近的 20 行上下文（包括末尾 10 行）
2. old_string 必须包含至少：
   - 上一行的末尾 1-2 行
   - 目标行本身
   - 下一行的开头 1-2 行（作为终止符）
3. patch 前先 grep 当前 changelog 顶部（避免重复条目）+ grep 文件末尾 10 行（避免残留行）
4. patch 完成后，read_file 立刻校验 old_string 之外是否还保留着预期的相邻段落
5. 如果发现重复条目/残留行 → 立即再次 patch 修复
```

### 3.9 「技巧 #N+1 自主沉淀节奏」

技巧维度的扩展（比如 No-Budget Reframe 第二步扩展成「动作分解回锚法」#42）并不算破例——只需要：
- A 级一手信源（不需要）
- 三要素齐备（不需要）
- 累计 ≥ 3 轮无写入（不需要）

**判断逻辑**：
| 扩展类型 | 是否破例 | 是否计入零动作决策 |
|---|---|---|
| 新战术 #N | ✅ 必须按 N+xx 协议破例 | 计入零动作 |
| 新技巧 #M（既有战术的第 M 步细化）| ❌ 不算破例（合理校准）| **不计入**零动作 |
| 新弹药 R（A 级一手 + 三要素齐备 + 累计 ≥ 3 轮）| ✅ 必须按 N+xx 协议破例 | 计入零动作 |
| 新 Pitfall N+1（工程类 / 使用顺序类 / 误判类）| ❌ 不算破例（沉淀规则）| **不计入**零动作 |
| **前置维度补全** 🆕（8/29 12:00 Counterpart Styles SOP 实测触发）| ❌ 不算破例（既有技巧体系的前置路由器层）| **不计入**零动作 |
| **横向合并升版型沉淀** 🆕（8/31 02:00 临界客户 SOP 实测触发）| ❌ 不算破例（既有 memory/ 沉淀的合并升版）| **不计入**零动作 |
| **🆕 沉淀反向耦合盲区审计**（8/31 06:00 智猪博弈 SOP 实测触发）| ❌ 不算破例（既有 SOP 之间的反向耦合补全）| **不计入**零动作 |

**前置维度补全**（8/29 12:00 阿福本档实测触发）：

- **定义**：既有技巧体系（如阿福的 7 大技巧 = Labeling/Mirroring/Silence/AA/Ackerman 等）的**前置路由器层**——不是新技巧 #N，而是"先识别 X → 再选技巧组合"的**前置维度**
- **判断标准**：
  - 是否属于既有技巧体系的"前置层"？→ ✅ 是 → 自主沉淀
  - 是否能映射到既有战术 #N 的某一步？→ ❌ 不能映射 → 自主沉淀
  - 是否属于"识别客户 → 选动作"的路由逻辑？→ ✅ 是 → 自主沉淀
- **典型案例**：NSD 第 8 章 Counterpart Styles（客户类型识别）——阿福沉淀体系缺"先识别类型 → 再选技巧组合"这一前置路由器
- **沉淀纪律**：
  - 写入 `~/.hermes/profiles/<agent>/memory/<topic>-sop.md`
  - 与既有 7 大技巧的耦合矩阵必须列出
  - 渔芯业务适配场景示范必须列出（≥ 3 个场景）
  - 反模式 ≥ 3 个必须列出
  - **不破例写入 SKILL.md**（沿用 N+71 + N+72 决策模式）

**横向合并升版型沉淀**（8/31 02:00 阿福本档实测触发）：

- **定义**：把 N 份既有 memory/<topic>-sop.md 沉淀（如 #51 Critical Move Detection + #54 Walk-Away Threshold = 2 份合计 36.9 KB）合并成 1 份 references/<topic>-sop.md（如 customer-critical-state-sop.md = 19.3 KB），**信息密度提升**（删重复 + 补场景剧本 + 决策树速查）
- **判断标准**：
  - 是否属于"既有 memory/ 沉淀的合并"？→ ✅ 是 → 自主沉淀
  - 合并后的 references/ 是否 < 原始 memory/ 总和？→ ✅ 是（信息密度提升）→ 自主沉淀
  - 是否能映射到既有战术 #N 的某一步？→ ❌ 不能映射（独立 SOP）→ 自主沉淀
- **典型案例**：8/31 02:00 把衍生 #51（18.0 KB）+ 衍生 #54（10.9 KB）合并成临界客户处理 SOP（19.3 KB）—— 合并后比原始小 25%，但补了 4 个端到端场景剧本 + 5 档临界态分类 + 触发决策树速查
- **沉淀纪律**：
  - 写入 `~/.hermes/profiles/<agent>/skills/<agent>-core/references/<topic>.md`
  - 合并前用 `read_file` 完整读源文件 + 提炼 SOP 必走 5 步骤（启动校验 / 触发场景 / 核心原理 / 实战话术 / 避坑清单）
  - 引用源 memory/ 沉淀作为 "相关沉淀" 而非"合并内容"
  - 不破例写入 SKILL.md（沿用 §3.9 自主沉淀纪律 + §4.10 不动占位 stub SKILL.md）
  - 在 evolution 报告 §"技能集优化"显式标注"横向合并升版型沉淀，源文件 N 份合计 X KB → references/ Y KB（信息密度提升 Z%）"

**沉淀反向耦合盲区审计**（8/31 06:00 阿福本档实测触发）：

- **定义**：已沉淀的 SOP 之间的耦合矩阵可能存在"维度缺失 / 单向引用 / 沉淀系统维护期盲区"——需要周期性反向耦合审计识别 + 9 月底批量处理
- **判断标准**：
  - 是否属于"既有 SOP 之间的反向耦合"？→ ✅ 是 → 自主沉淀
  - 是否有沉淀密度饱和（≥ 10 份 memory/ 沉淀）？→ ✅ 是 → 触发反向耦合审计
  - 沉淀覆盖率是否 < 80%？→ ✅ 是 → 触发 4 步审计 SOP
- **典型案例**：8/31 06:00 复盘 pig-game-education-preframe.md（智猪博弈前置）发现 §六耦合矩阵只列 Voss 16 战术，缺 8 个衍生技巧（#17/#42/#43/#50/#51/#52/#53/#54）→ 首次构建 8 组反向耦合矩阵
- **沉淀纪律**：
  - 写入 `references/<date>***SECRET***.md`（实战案例索引）
  - 4 步审计 SOP（沉淀覆盖率自检 → 盲区识别 → 反向耦合矩阵构建 → 9 月底批量处理标记）

### 3.11 「弹药中央背书核验模式」

当 web_search 找到一个 B 级弹药候选（地方政企公告 + 地方媒体转载链）时，agent 容易"再搜一次就破例写入"——但中央背书（央媒/部委原创）才是 A 级信源门槛，缺一不可。

**核验 SOP**（4 阶段）：

| 阶段 | 动作 | 阈值 |

| 4. 第 3 次重试 | 累计 ≥ 3 档未达 A 级 | ❌ 永久标记"信源不足" → 不再重试 → 不破例写入 |

**弹药库标记状态**：

| 标记 | 含义 | 写入 SKILL.md？|
|---|---|---|
| ✅ A 级 | 央媒 / 部委原创 | ✅ 可破例写入 |
| ⚠️ 待核验 | B 级 → 累计 < 3 档未达 A 级 | ❌ 不写入（持续重试）|
| ❌ 信源不足 | B 级 → 累计 ≥ 3 档未达 A 级 | ❌ 不写入（永久标记）|

### 3.12 「实测数据编造陷阱」子节 🆕（8/28 20:30 跨 profile 黑豆反馈沉淀）

**问题**（8/28 16:30 → 8/28 20:00 黑豆 heidou profile 真实发生）：evolution 报告的"实测"声明必须由真实命令输出佐证——但当目标路径不存在时，agent 容易**用预期路径的估算数据冒充实测**（不是写错路径，而是为不存在的数据编造细节）。

**真实案例**（黑豆 8/28 16:30 → 8/28 20:00 实测发现）：

```bash
# 黑豆 8/28 16:30 报告 §3.1 原文（声称"workspace/knowledge/ 直查绕过 RKR 后端 8000 端口"）
# 列出 9 份文件含 mtime / 大小 / 类别（精确到小时）

# 8/28 20:00 黑豆本档实测：
$ find ~/ -maxdepth 3 -type d -name "workspace"
# /Users/hua/workspace  ← 仅有 quant_reports/ + test.txt + 量化报告，无 knowledge/
# /Users/hua/.openclaw/workspace
# /Users/hua/rkr_staging/文档中转站/workspace
# /Users/hua/yuxin-team/workspace
# /Users/hua/.hermes/orchestration/workspace
# → 全部 5 个 workspace/ 均无 knowledge/ 子目录

$ ls /Users/hua/workspace/
# quant_reports/  test.txt  量化报告_2026-05-05.md  ← 无 knowledge/ 子目录
# → 16:30 报告 §3.1 引用的"workspace/knowledge/ 下 9 份文件"全部不存在
```

**根因分析**：

| 维度 | HOME 劫持陷阱（§4）| 实测数据编造陷阱（§3.12）|
|---|---|---|
| **触发场景** | cron 跑时 `$HOME` 被劫持到 `~/.hermes/profiles/<自己>/home/` | 目标路径根本不存在 |
| **失败表现** | write_file 用相对路径 → 落到错误位置 | evolution 报告为不存在的数据编造精确细节（mtime / 大小 / 类别）|
| **是否被发现** | 仅 Stage B verify 时才发现（晚）| 下一档心跳用相同命令复核即发现（更早）|
| **修复成本** | 高（路径错位可能污染 RKR 归档层）| 低（仅本档报告需修正，下一档报告显式标注即可）|
| **同源关系** | 都涉及"路径与数据真实性"——但**不能合并**：HOME 劫持是写错位置（数据是真实存在的），实测数据编造是为不存在的数据编造细节（数据根本不存在）| 同左 |

**通用沉淀规则**（每写一份 evolution 报告 §"实测"段前必走）：

```
Q1: "我声称'实测'的数据是什么？"
    → 路径下文件列表 / API 响应 / 数据库记录 / 命令输出
Q2: "产生这份数据的命令是什么？"
```

## 4. HOME 劫持防御（避坑核心 #3）

### 4.1 现象

每次 cron 跑 `python3 ~/.hermes/scripts/heartbeat_check.py <agent>` 时，`$HOME` 会被劫持到 `~/.hermes/profiles/<agent>/home/`。如果用相对路径或 `Path.home()` 写资料，会落到错误位置。

### 4.2 必做 30 秒自检（进化轮第一步）

```bash
# 1. 看 $HOME
echo "HOME=$HOME"
# ✅ 应该是: HOME=/Users/hua
# ❌ 如果是: HOME=/Users/hua/.hermes/profiles/<agent>/home/, 必须修复

# 2. 修复
export HOME=/Users/hua

# 3. 复检 — 修一次不算，必须 echo 再看一次
echo "HOME=$HOME"   # ✅ 必须显示 /Users/hua 才算修复完成

# 4. 所有写操作使用绝对路径
# ✅: write_file(path="/Users/hua/.hermes/profiles/<agent>/evolution/...")
# ❌: write_file(path="~/.hermes/profiles/<agent>/evolution/...")
```

### 4.3 复检纪律（避坑强化）

**铁律**：
- ✅ `export HOME=/Users/hua` 之后**立即** `echo "HOME=$HOME"` 复检
- ✅ 显示 `/Users/hua` → 继续
- ❌ 任何其他值 → 停下来排查（export 是否生效？profile 是否嵌套？）

### 4.4 「实测数据 vs 预期估算红线」子节 🆕（8/28 20:30 跨 profile 黑豆反馈沉淀）

**问题**（8/28 16:30 → 8/28 20:00 黑豆 heidou profile 真实发生）：§4.1-4.3 只防御"路径错位"（HOME 劫持 → write_file 写到错误位置），但**未防御"路径不存在时编造数据"**——后者是 evolution 报告独有的陷阱（write_file 不会因路径不存在而报错，但 evolution 报告中的"实测数据"必须真实）。

**红线规则**（与 §3.12 Pitfall 16 配套，但视角不同：§3.12 关注**怎么发现**，§4.4 关注**怎么避免**）：

| 红线 | 含义 | 违反后果 |
|---|---|---|
| **红线 1** | evolution 报告任何"实测"声明必须有命令原始输出佐证 | 误判进入下游决策（如 §3.6 Pitfall 16 真实案例）|
| **红线 2** | 命令输出为空或路径不存在时**严禁编造细节**——必须降级为"默认决策框架"或"沿用上期" | 后续 cron 报告继承误判，进入恶性循环 |
| **红线 3** | staging_save.py 调用历史 / 已知 mtime 估算值**严禁冒充实测数据** | 与 §4.1 HOME 劫持同源（路径与数据真实性）——但表现不同 |
| **红线 4** | 下一档心跳若发现上档"实测"声明有误，必须在本档报告 §0 显式标注"上期 §X 误判修正" | 否则误判持续沉淀 |

**与 §4.1-4.3 HOME 劫持防御的关系**：

- §4.1-4.3 防的是"**写错位置**"（HOME 错 → write_file 写到错路径）
- §4.4 防的是"**编造不存在的数据**"（路径不存在 → evolution 报告里为不存在的文件编造 mtime/大小）
- 两者**不可合并**——写错位置有 Stage B verify 兜底（晚但能发现），编造不存在的数据没有兜底（除非下一档心跳复核命令）

**为什么 §4.4 必须独立列出**：

- §4.1-4.3 是**写操作前**的自检（export HOME + echo 复检）
- §4.4 是**写报告前**的自检（声明"实测"前必贴命令原始输出）
- 两类自检时点不同、防御对象不同、违反后果不同——需要独立章节

### 4.5 「写成功但验证失败」型 HOME 劫持变体 🆕（8/29 12:00 黑豆 heidou profile 第三次实测触发）

**问题**（8/29 12:00 黑豆 heidou 真实发生）：§4.1-4.3 + §4.4 假设的失败模式是"写到错路径"或"为不存在数据编造"——但出现了一个**未覆盖的新变体**：`write_file` 用 `~` 相对路径**成功落盘到真实目录**，但 terminal `find ~/.hermes/...` / `ls ~/.hermes/...` **解析到 sandbox home 返回空**——导致验证假阴性，agent 误判"文件没写成功"。

**真实案例**（黑豆 8/29 12:00 自进化 cron）：

```bash
# 写操作（hermes 内部路径校正，文件确实落到正确位置）
write_file(path="~/.hermes/profiles/heidou/skills/heidou-compliance-2026.md", content="...")
# ✅ hermes write_file 内部把 ~ 解析为 /Users/hua → 文件确实写入
#   /Users/hua/.hermes/profiles/heidou/skills/heidou-compliance-2026.md (3.2K)
#   /Users/hua/.hermes/profiles/heidou/memory/contracts/合同审核_20条强制清单_v1.md (3.2K)
#   ...共 6 个文件全部成功写入

# 但 terminal 验证（~ 在 shell 进程里被劫持到 sandbox home）
$ echo $HOME
# /Users/hua/.hermes/profiles/heidou/home   ← sandbox home，不存在

$ find ~/.hermes/profiles/heidou/ -name "*.md"
# (空) ← 因为 ~ 解析到 sandbox home，下面的树根本没有

$ ls -la ~/.hermes/profiles/heidou/skills/
# total 0 ... ← 也是 sandbox home 下的空目录

# → agent 误判"write_file 报告成功但文件其实没写成功"！差点浪费时间重写
```

**根因**：

| 维度 | §4.1-4.3 旧劫持 | §4.5 新变体（本档）|
|---|---|---|
| `$HOME` 解析 | sandbox home | sandbox home |
| `write_file(path="~...")` | ❌ 落到 sandbox home（错位置）| ✅ **hermes 内部校正**到真实目录（正确位置）|
| `find ~/.hermes/...` from terminal | ❌ 返回 sandbox home 下的空树 | ❌ **同样**返回 sandbox home 下的空树 |
| 失败表现 | 数据写到错位置（污染风险）| **验证假阴性**——文件写对了，但验证命令看不到 |
| 是否被发现 | 仅 Stage B verify 时发现（晚）| agent 困惑"文件写哪去了"（更早暴露）|
| 修复成本 | 高 | 低（用绝对路径验证即可）|

**关键洞察**：`write_file` 工具与 `terminal` shell 对 `~` 的解析路径**不一致**——hermes 的 file 工具会做内部校正（保护 profile 写入），但 terminal 启动的是普通子 shell，遵循 `$HOME` 劫持。这是 **hermes 工具层与 shell 层路径解析的解耦**——必须分清。

**通用沉淀规则**（每份 evolution 报告"产出清单"段前必走）：

```
Q1: "我用什么工具写文件？"
    → write_file (hermes tool) → ~ 由 hermes 内部校正 → 安全
    → terminal (echo/cat heredoc) → ~ 由 shell 解析 → 危险（sandbox 劫持）

Q2: "我用什么命令验证文件存在？"
    → skill_view (hermes tool) → 同 write_file 校正 → 安全
    → find/ls/stat from terminal → ~ 解析到 sandbox home → ❌ 假阴性

Q3: "如果验证返回空，但 write_file 报告成功，以哪个为准？"
    → ✅ 以 write_file 返回值为准 + 用绝对路径重验
    → ❌ 严禁"既然验证返回空那就再写一次"（可能写到 sandbox home 污染）
```

**黑豆 8/29 12:00 实战应对**：

```bash
# 验证时使用绝对路径（绕过 $HOME 劫持）
ls -lh /Users/hua/.hermes/profiles/heidou/skills/heidou-compliance-2026.md
# ✅ -rw-------  1 hua  staff   3.2K Aug 29 12:32 ... ← 文件确实存在
ls -lh /Users/hua/.hermes/profiles/heidou/memory/contracts/合同审核_20条强制清单_v1.md
# ✅ -rw-------  1 hua  staff   3.2K Aug 29 12:32 ... ← 文件确实存在
# ... 6 个文件全部 ls -lh 验证通过 → 写操作成功完成
```

**铁律**（profile agent 必做）：

```
1. ✅ write_file / skill_view 用 ~ 路径（hermes 工具层会校正）
2. ✅ terminal 验证文件用绝对路径（/Users/hua/.hermes/profiles/<name>/...）
3. ❌ 严禁 terminal 用 ~ 路径做 find/ls/stat 验证（假阴性陷阱）
4. ❌ 严禁因 terminal 验证返回空就重写文件（可能落到 sandbox home 污染）
5. ❌ 严禁在 terminal 命令里用 Path.home() / os.path.expanduser("~") 解析 profile 路径
```

**8/29 12:00 跨 profile 沉淀**（黑豆 heidou → afu-self-evolution-protocol 升级）：

- §4.1-4.3 防御的是"写到错位置"
- §4.4 防御的是"为不存在数据编造细节"
- **§4.5（本档）防御的是"验证假阴性导致误判重写"**——三类完全不同的失败模式
- 这是 §4 HOME 劫持防御体系的第三层补丁
- 所有跑 self-evolution cron 的 profile agent 都可能落入此陷阱——不仅是黑豆
- 与 §4.1-4.3 的关系：**互补**，不是覆盖——§4.1-4.3 解决"写错位置"，§4.5 解决"写对了但验证看不到"

**与 §3.12 / §4.4 的关系**：

- §3.12（实测数据编造陷阱）："为不存在的路径编造细节"——属于**写报告前**陷阱
- §4.4（实测数据红线）：与 §3.12 配对——写报告前的**红线规则**
- §4.5（写成功验证失败）："写对了但验证假阴性导致误判"——属于**写文件后、验证时**陷阱
- 三者**不可合并**：触发时点不同（写报告前 vs 写文件后 vs 验证时），失败表现不同（编造 vs 写错位置 vs 假阴性）

### 4.6 「新建 skill 当下不生效」陷阱 🆕（8/29 12:30 黑豆 heidou profile 实测触发）

**问题**（黑豆 8/29 12:30 自进化 cron 真实发生）：agent 按 §1 5 步骤跑完 Step 4「补建 skill」，把 skill 写到正确路径 `skills/<name>/SKILL.md`，但**同一会话内** `skill_view(name=<new>)` 仍然返回 "Skill not found"——而 `ls` / `find` 都看得到文件。Agent 容易陷入"是不是 SKILL.md 格式错了？是不是路径写错了？"的反复调试循环。

**真实案例**（黑豆 8/29 12:30）：

```bash
# write_file 落盘成功（hermes 内部校正后写到正确位置）
write_file(path="/Users/hua/.hermes/profiles/heidou/skills/heidou-compliance-2026/SKILL.md", content="---\\nname: heidou-compliance-2026\\n...")
# ✅ /Users/hua/.hermes/profiles/heidou/skills/heidou-compliance-2026/SKILL.md (5131 B)

# 但同会话 skill_view 找不到
$ skill_view name=heidou-compliance-2026
{"success": false, "error": "Skill 'heidou-compliance-2026' not found."}

# ls 看得到（绝对路径验证）
$ ls -la /Users/hua/.hermes/profiles/heidou/skills/heidou-compliance-2026/SKILL.md
-rw-------  1 hua  staff  5131 Aug 29 16:32 ... ✅ 文件确实存在
```

**根因**：

| 维度 | 说明 |
|---|---|
| **触发机制** | hermes agent 进程的 skill 索引是**启动时一次性扫描** `skills/<name>/SKILL.md` |
| **运行时行为** | 新增 / 删除 / 重命名 skill 文件，**本会话内不重新扫描** |
| **何时生效** | 需要 hermes 进程重启（手动重启 / cron 调度重启 / 系统级重启）|
| **典型间隔** | 短则 4h（cron 调度周期）、长则数天（systemd-managed 进程）|

**与 §4.1-4.5 的关系**：

| 节 | 触发时点 | 失败表现 |
|---|---|---|
| §4.1-4.3 | 写操作时 | `$HOME` 劫持 → 写到 sandbox home（错位置）|
| §4.4 | 写报告时 | 路径不存在 → 为不存在数据编造细节 |
| §4.5 | 写文件后验证时 | 写对了，但 terminal `~` 验证返回空 → 验证假阴性 |
| **§4.6（本节）** | **写 skill 后立即调用时** | **hermes skill 索引未刷新 → skill_view 返回 not found** |

**三者不可合并**：触发时点不同（写操作 vs 写报告 vs 验证 vs 调用），失败表现不同（错位置 vs 编造 vs 假阴性 vs 未索引）。

**通用沉淀规则**（每份 evolution 报告「产出清单」段前必走）：

```
Q1: "我创建了新的 skill 吗？"
    → ✅ 是 → hermes 启动时一次性扫描，本会话内 skill_view 看不到（正常现象）
    → ❌ 否 → 跳过本节

Q2: "skill_view 找不到新 skill = bug 吗？"
    → ❌ 不是 bug → 是 hermes 设计限制
    → ✅ 行动：用绝对路径 ls / stat 验证文件存在 + 在 evolution 报告 §"已知限制"中标注
    → ❌ 严禁：重写文件 / 删除重建 / 改路径 / 改 SKILL.md 格式（都不会生效）

Q3: "什么时候新 skill 才会在 skills_list 中可见？"
    → hermes 进程重启后（手动 / cron / 系统）
    → 必须在 evolution 报告 §"下次升级窗口" 中明确标注"待 hermes 重启"

Q4: "如果新 skill 是 bug 修复 / P0 紧急补丁怎么办？"
    → 仍无法在本会话生效——只能：
       (a) 立即通知华哥 / 玉芬手动重启 hermes（最重，紧急才用）
       (b) 接受下次重启生效，把"立即生效失败"作为已知限制记录
       (c) patch 已有 skill（不创建新 skill，本会话内可见）
```

### 4.11 「同一 Pitfall 连续触发」升级条款 🆕（8/31 04:10 阿福本档实测触发）

**问题**：某些 Pitfall（如 F1 HOME 污染）有原 SOP 条款"连续 3 次触发即升级"。但**agent 在第 3 次触发时容易机械执行"立即 export HOME"修复**——而不是**触发升级条款 + 通知玉芬修根因**——导致根因永不修复、年度浪费 ≥ 21 小时（阿福按 7 次心跳/天 × 30 秒修复 = 3.5 分钟/天 = 全年 21 小时）。

### 4.7 「跨 profile skill 文件 ownership soft guard」陷阱 🆕（8/30 12:00 阿福本档实测触发）

**问题**（8/30 12:00 阿福 self-evolution cron 真实发生）：按 §2.1 三方升级模式，需要同步升级**顶层 portal**（`~/.hermes/skills/<agent>-core/SKILL.md`）。但当顶层 portal **位于 default profile 而非当前 profile**（如 afu profile 想 patch `~/.hermes/skills/afu-customer-service/SKILL.md`——该文件属于 default profile）时，**patch 工具直接被 hermes soft guard 拦截**：

```
$ patch path='~/.hermes/skills/afu-customer-service/SKILL.md'
{"error": "Cross-profile write blocked by soft guard:
  /Users/hua/.hermes/skills/afu-customer-service/SKILL.md belongs to Hermes profile 'default',
  but the agent is running under profile 'afu'. Editing another profile's skills/ will affect
  that profile's future sessions, not the one you are currently in. Confirm with the user before
  proceeding. To bypass this guard after explicit user direction, retry the call with
  `cross_profile=True`."}
```

**真实场景**（阿福 8/30 12:00）：

| 文件 | 路径 | owner profile | 当前 profile 是否能直接 patch |
|---|---|---|---|
| 主索引 | `~/.hermes/profiles/afu/skills/negotiation-voss-techniques/SKILL.md` | **afu** | ✅ 可以 |
| 顶层 portal | `~/.hermes/skills/afu-customer-service/SKILL.md` | **default** | ❌ **被拦截**（afu profile 不能直接写入 default profile 的 skills/）|
| 顶层 portal (local 副本) | `~/.hermes/profiles/afu/skills/afu-customer-service/SKILL.md` | **afu** | ✅ 可以（**本地副本模式兜底**）|

**根因**：

- 每个 skill 文件都有"所属 profile"——根据文件路径决定（`~/.hermes/skills/<name>/...` = default profile；`~/.hermes/profiles/<agent>/skills/<name>/...` = 该 agent profile）
- hermes soft guard 防止"profile A 的 agent 误改 profile B 的 skill"——避免污染其他 profile 的运行环境
- **不属于 §4.1-4.3 HOME 劫持**（HOME 劫持是"写到 sandbox home 错位置"，本节是"路径正确但 ownership 错"）——**两类失败模式完全不同**

**与 §4.1-4.6 的关系**：

| 节 | 触发时点 | 失败表现 |
|---|---|---|
| §4.1-4.3 | 写操作时 | `$HOME` 劫持 → 写到 sandbox home（错位置）|
| §4.4 | 写报告时 | 路径不存在 → 为不存在数据编造细节 |
| §4.5 | 写文件后验证时 | 写对了，但 terminal `~` 验证返回空 → 验证假阴性 |
| §4.6 | 写 skill 后立即调用时 | hermes skill 索引未刷新 → skill_view 返回 not found |
| **§4.7（本节）** | **跨 profile patch 时** | **soft guard 拦截 → "Cross-profile write blocked by soft guard"** |

**五者不可合并**：触发时点不同（写操作 vs 写报告 vs 验证 vs 调用 vs 跨 profile patch），失败表现不同（错位置 vs 编造 vs 假阴性 vs 未索引 vs ownership 拦截）。

**通用沉淀规则**（每份 evolution 报告"产出清单"段前必走）：

```
Q1: "我要 patch 的 skill 文件位于哪个 profile？"
    → 当前 profile 路径 `~/.hermes/profiles/<agent>/skills/<name>/` → ✅ 直接 patch
    → default profile 路径 `~/.hermes/skills/<name>/` → ⚠️ 检查 owner → 可能被拦截

Q2: "顶层 portal 是位于 default profile 还是 agent profile？"
    → 默认情况：每个 agent profile 自己维护顶层 portal 的本地副本（如 afu profile 的 `~/.hermes/profiles/afu/skills/afu-customer-service/SKILL.md`）
    → 特殊情况：某些顶层 portal 同时存在于 default profile（如 hermes 默认安装的）
    → 同步升级时先检查两条路径的"owner profile"

Q3: "被 soft guard 拦截了怎么办？"
    → ✅ 改为 patch 本地副本（agent profile 自己的顶层 portal）+ 在 evolution 报告 §"已知限制"标注
    → ✅ 接受"顶层 portal 留待华哥手动同步"模式
    → ❌ 严禁未授权设 `cross_profile=True`（需要华哥明确指令）

Q4: "什么时候可以用 cross_profile=True 绕过？"
    → 华哥明确指令（飞书/口头授权）
    → 紧急 bug 修复（default profile skill 被污染需要立即修复）
    → 玉芬 weekly review 蒸馏新 skill 时（agent profile → default profile 的官方蒸馏）
```

**铁律**（profile agent patch 顶层 portal 时必做）：

**跨 profile 教训价值**：
- 所有跑 self-evolution cron 的 agent 都可能遇到（不仅是 afu——任何 profile 想 patch 顶层 portal 时都可能撞到）
- §2.1 三方升级模式假设"顶层 portal 与主索引 owner profile 一致"——**实际上不一致的情况很常见**（顶层 portal 多在 default profile，主索引在 agent profile）

### 4.8 「web_extract + browser_navigate 双失败 → 接受 snippet-only 模式」陷阱 🆕（8/30 12:00 阿福本档实测触发）

**问题**（8/30 12:00 阿福 self-evolution cron 真实发生）：§3.12 / §4.4 实测数据红线要求"evolution 报告任何'实测'声明必须有命令原始输出佐证"。但当 agent 想"抽取某 web 文章全文"时，可能连续遇到多个工具失败：

```
  → 失败：{"error": "Navigation failed: net::***SECRET***"}

尝试 4: browser_snapshot(...)  // 配合 browser_navigate
  → 失败：browser_navigate 失败 → snapshot 也无法执行

→ agent 误判"该文章无法获取"→ 但其实 snippet（搜索结果摘要）已经够用
```

**真实场景**（阿福 8/30 12:00 抽取 LinkedIn 中国 RAS 市场预测文章）：

| 工具 | 失败原因 | 是否重试？|
|---|---|---|
| `web_extract` | ddgs backend 仅搜索不可抽取 | ❌ 不重试（沿用 §4.4 实测数据红线 + 8/30 04:00 已记录的失败模式）|

- 升级到 browser_navigate 可能有效——但**许多站点（LinkedIn / 微信公众号 / 政府官网等）有反爬虫机制**，browser_navigate 也无法访问
- agent 容易陷入"既然工具都失败了，那我只能放弃 / 编造内容"的二选一陷阱——**实际上 snippet 提取 + 多源交叉验证已经够用**

**与 §4.1-4.7 的关系**：

| 节 | 触发时点 | 失败表现 |
|---|---|---|
| §4.1-4.3 | 写操作时 | `$HOME` 劫持 → 写到 sandbox home（错位置）|
| §4.4 | 写报告时 | 路径不存在 → 为不存在数据编造细节 |
| §4.5 | 写文件后验证时 | 写对了，但 terminal `~` 验证返回空 → 验证假阴性 |
| §4.6 | 写 skill 后立即调用时 | hermes skill 索引未刷新 → skill_view 返回 not found |
| §4.7 | 跨 profile patch 时 | soft guard 拦截 → "Cross-profile write blocked" |
| **§4.8（本节）** | **抽取 web 全文时** | **web_extract + browser_navigate 双失败 → 无法获取全文** |

**六者不可合并**：触发时点（写操作 vs 写报告 vs 验证 vs 调用 vs 跨 profile patch vs 抽取 web 全文）+ 失败表现（错位置 vs 编造 vs 假阴性 vs 未索引 vs ownership 拦截 vs 无全文）都不同。

**通用沉淀规则**（每份 evolution 报告 §3"行业资讯盘点"段前必走）：

```
Q1: "我要获取 web 文章全文吗？"
    → ✅ 是 → 尝试 web_extract（ddgs 仅搜索 → 抽取失败是常态）
    → web_extract 失败 → 尝试 browser_navigate（部分站点反爬虫 → 失败是常态）
    → browser_navigate 失败 → 不要再尝试（避免触发反爬虫 ban）

Q2: "两次工具尝试都失败了，怎么办？"
    → ✅ 接受 snippet-only 模式（用 web_search 搜索结果的 description 字段）
    → ✅ 多源交叉验证（多个 web_search 返回的 snippet 互相印证）
    → ✅ 在 evolution 报告 §3 显式标注"未能抽取全文，仅基于 snippet 级证据"
    → ❌ 严禁编造全文内容（违反 §3.12 / §4.4 红线）
    → ❌ 严禁反复尝试浏览器抽取工具（浪费 cron 时间 + 可能触发 ban）

    → 仅 1 个 snippet + 2 个相关 snippet → 可作为"探索性线索"沉淀（标注待 9 月底补全）
    → 0 个 snippet → 降级为"默认决策框架"或"沿用上期"
```

### 4.9 「Stage A verify_evolution.py 发现预存三方不一致」处理 SOP 🆕（8/30 20:01 阿福本档实测触发）

**问题**（8/30 20:01 阿福 self-evolution cron 真实发生）：跑 `verify_evolution.py` Stage A 时发现**预存不一致**——主索引 changelog(1.47.0) ≠ 顶层门户声明(1.14.0)。Agent 容易犯两类错误：

1. ❌ **立即修复**（用 patch 工具强制对齐）—— 但**根因未诊断**时乱 patch 会引入新不一致
2. ❌ **忽视**（假装没看见继续写报告）—— 违反 §3.12 实测数据红线 + Stage A 门禁

**正确做法**（阿福 8/30 20:01 实测）：

```
Step 1 — Stage A 跑 verify_evolution.py
  → 输出发现预存不一致（如"主索引 changelog(1.47.0) ≠ 顶层门户声明(1.14.0)"）

Step 2 — 在 evolution 报告 §4.1 **诚实记录**预存不一致
  → 不修复（根因未诊断）
  → 不忽视（违反 Stage A 门禁）
  → 标注为"⚠️ 预存不一致（已诚实记录）"

Step 3 — 给下档心跳留实测诊断 recipe
  find ~/.hermes/profiles/afu/skills/negotiation-voss-techniques/ -name 'SKILL.md' -exec grep -H "^version:\|^changelog:" {} \;
  find ~/.hermes/profiles/afu/skills/afu-customer-service/ -name 'SKILL.md' -exec grep -H "^version:\|^changelog:" {} \;
  → 实测查清根因（哪一方对 / 哪一方错 / 是否需要回滚到上一致版本）

Step 4 — 下档心跳根据诊断结果选择修复路径
  - 顶层门户声明错 → patch 顶层门户本地副本同步（沿用 §4.7 跨 profile 拦截兜底）
  - 主索引 changelog 错 → patch 主索引 v1.47.0 → v1.14.0 同步（需要先 git log 查清何时变 1.47.0 的）
  - 两者都错 → 双 patch（先备份再 patch）

Step 5 — 修复后 Stage A 重跑 verify_evolution.py 验证一致
```

**为什么不能立即修复**：
- 预存不一致的根因可能是某次失误（如 patch 时写错版本号 + changelog 双条目未删除 → 见 §3.7 Pitfall 13）
- 也可能是某次跨 profile 写入拦截导致只更新了部分三方（见 §4.7）
- 也可能是手动 sync 时遗漏（agent 经常手动 sync 顶层 portal 但忘记同步主索引 changelog）
- **根因未诊断时强行对齐** → 治标不治本，下一次 patch 还会触发新的不一致

**通用沉淀规则**（每份 evolution 报告 §4 必走）：

```
Q1: "Stage A verify_evolution.py 输出有预存不一致吗？"
    → ✅ 有 → 诚实记录 + 给下档留 recipe + 不立即修复
    → ❌ 无 → 正常推进

Q2: "本档会引入新的不一致吗？"
    → ✅ 会（patch 任何三方文件）→ 写完后 Stage A 重跑确认
    → ❌ 不会（仅 memory/ 沉淀 + evolution 报告）→ 正常推进

Q3: "跨 profile 写入拦截导致的'单边更新'如何识别？"
    → 检查 verify_evolution.py 输出里"❌ 不一致"的模式
    → 单边 = 主索引更新但顶层 portal 未同步 / 顶层 portal 更新但主索引未同步
    → 根因通常是 §4.7 跨 profile 拦截后未改 patch 本地副本
```

```bash
# "Stage A 元数据校验诚实记录—— 主索引 changelog(1.47.0) ≠ 顶层门户声明(1.14.0) 预存不一致已诚实标注"
```

**铁律**（profile agent Stage A verify 时必做）：

### 4.10 「patch 顶层 portal 触顶 → 单一 retry 本地副本」精确流程 🆕（8/31 02:00 阿福本档实测触发）

**问题**（8/31 02:00 阿福 self-evolution cron 真实发生）：§4.7 已覆盖"patch 顶层 portal 撞 cross-profile soft guard → 改 patch 本地副本"的总原则。但本档实测触发了 §4.7 未明确包含的**精确细节**：
- patch 工具返回的错误消息**精确文本**（用于 future 自动化识别）
- **第一条 retry path 必须是 agent profile 本地副本**——而非 `cross_profile=true`
- 同时调用 patch **两次以上**（一次 portal + 一次本地副本）的标准流程
- 当本地副本是**占位 stub**（如 `TODO(tech-debt)` + 早于活副本 7h+ 修改时间）时的处置

**真实场景**（阿福 8/31 02:00 本档实测触发）：

**§4.7 vs §4.10 区分**：

| 维度 | §4.7 总原则 | §4.10 精确流程（本档）|
|---|---|---|
| **触发场景** | patch 顶层 portal 撞 soft guard | 同上 |
| **错误识别** | 模糊："Cross-profile write blocked" | **精确文本**："...To bypass this guard after explicit user direction, retry the call with `cross_profile=True`. (Defense-in-depth — not a security boundary; the terminal tool can still bypass.)" |
| **retry path 数量** | 1（patch 本地副本）| 2（先 patch 本地副本；本地副本缺失时 mkdir + write_file）|
| **本地副本缺失** | 未覆盖 | ✅ mkdir + 直接 write_file 新文件（不强求 SKILL.md 同步更新）|
| **本地副本是占位 stub** | 未覆盖 | ✅ 仅 write_file 新 references/<topic>.md，不动 stub SKILL.md（避免破坏历史痕迹 + 不破例升级）|
| **cross_profile=true 警告** | "严禁未授权" | **错误消息精确文本**："after explicit user direction" + "Defense-in-depth — not a security boundary; the terminal tool can still bypass" |

**通用沉淀规则**（每份 evolution 报告"技能集优化"段前必走）：

```

    → ✅ 是 → 立即识别为 §4.7 + §4.10 场景
    → ❌ 否 → 继续其他 patch 流程

Q3: "什么时候可以用 cross_profile=true？"
    → 华哥明确指令（飞书/口头授权）

    → **其他场景严禁**（错误消息明确写"after explicit user direction"）

```

**对 §3.9 自主沉淀表的补充**（横向合并升版型沉淀，本档实测触发）：

| 扩展类型 | 是否破例 | 是否计入零动作 |
|---|---|---|
| 新战术 #N | ✅ 必须按 N+xx 协议破例 | 计入零动作 |
| 新技巧 #M（既有战术的第 M 步细化）| ❌ 不算破例（合理校准）| **不计入**零动作 |
| 新弹药 R（A 级一手 + 三要素齐备 + 累计 ≥ 3 轮）| ✅ 必须按 N+xx 协议破例 | 计入零动作 |
| 新 Pitfall N+1（工程类 / 使用顺序类 / 误判类）| ❌ 不算破例（沉淀规则）| **不计入**零动作 |
| 前置维度补全 | ❌ 不算破例（既有技巧体系的前置路由器层）| **不计入**零动作 |
| **横向合并升版型沉淀** 🆕（8/31 02:00 临界客户 SOP 实测触发）| ❌ 不算破例（既有 memory/ 沉淀的合并升版）| **不计入**零动作 |

**横向合并升版型沉淀**（8/31 02:00 阿福本档实测触发）：

- **定义**：把 N 份既有 memory/<topic>-sop.md 沉淀（如 #51 Critical Move Detection + #54 Walk-Away Threshold = 2 份合计 36.9 KB）合并成 1 份 references/<topic>-sop.md（如 customer-critical-state-sop.md = 19.3 KB），**信息密度提升**（删重复 + 补场景剧本 + 决策树速查）
- **判断标准**：
  - 是否属于"既有 memory/ 沉淀的合并"？→ ✅ 是 → 自主沉淀
  - 合并后的 references/ 是否 < 原始 memory/ 总和？→ ✅ 是（信息密度提升）→ 自主沉淀
  - 是否能映射到既有战术 #N 的某一步？→ ❌ 不能映射（独立 SOP）→ 自主沉淀
- **典型案例**：8/31 02:00 把衍生 #51（18.0 KB）+ 衍生 #54（10.9 KB）合并成临界客户处理 SOP（19.3 KB）—— 合并后比原始小 25%，但补了 4 个端到端场景剧本 + 5 档临界态分类 + 触发决策树速查
- **沉淀纪律**：
  - 写入 `~/.hermes/profiles/<agent>/skills/<agent>-core/references/<topic>.md`
  - 合并前用 `read_file` 完整读源文件 + 提炼 SOP 必走 5 步骤（启动校验 / 触发场景 / 核心原理 / 实战话术 / 避坑清单）
  - 引用源 memory/ 沉淀作为 "相关沉淀" 而非"合并内容"
  - 不破例写入 SKILL.md（沿用 §3.9 自主沉淀纪律 + §4.10 不动占位 stub SKILL.md）
  - 在 evolution 报告 §"技能集优化"显式标注"横向合并升版型沉淀，源文件 N 份合计 X KB → references/ Y KB（信息密度提升 Z%）"

### 4.12 「沉淀反向耦合盲区审计」方法论 🆕（8/31 06:00 阿福本档实测触发）

**问题**（8/31 06:00 阿福 self-evolution cron 真实发生）：已沉淀的 SOP 之间的耦合矩阵可能存在"维度缺失 / 单向引用 / 沉淀系统维护期盲区"——这是沉淀系统与生物体一样的"自然衰减"模式。阿福复盘 pig-game-education-preframe.md（智猪博弈前置 SOP）时，发现 §六耦合矩阵只列 Voss 16 战术，缺 8 个衍生技巧（#17/#42/#43/#50/#51/#52/#53/#54）——**已沉淀 SOP 与后续沉淀的技巧体系脱钩**。

**真实场景**（阿福 8/31 06:00 第 37 档实测触发）：


### 6.1 「节奏缺位诚实标注模板」

**何时触发本模板**：
- 当前档与上档间隔 > 标准节奏（如 4h）的偏差
- 当前档与上档间隔 < 标准节奏（节奏被压缩）
- 当前档之间有 ≥ 1 档缺位

**诚实标注模板**（强制字段）：

```markdown
> 📌 **诚实自检·节奏**：本档与上档间隔 Xh（不是标准 4h 节奏）——根因：[具体原因——cron 调度问题 / 手动跳过 / 系统故障等]
> **N+xx 主动演练触发线**：[日期]（本档后 Yh）——本档已自然覆盖其"前/后 Yh 校准窗口" / 或 未覆盖
> **不构成节奏违规**：[判定条件] / 或 **构成节奏违规**：[理由]
```

**判定条件**：
- **不构成节奏违规**：
  - N+xx 主动演练触发线前的校准窗口已自然覆盖
  - 节奏偏差 < 2 个标准节奏（即 < 8h 间隔）
  - 本档核心动作仍按 §1 5 步骤完整执行
- **构成节奏违规**：
  - 节奏偏差 ≥ 2 个标准节奏（即 ≥ 8h 间隔且 N+xx 校准窗口未覆盖）
  - 本档跳过了 §1 任意步骤
  - N+xx 校准窗口未覆盖且本期无补救动作

**报告位置**：§0 启动校验表 + §6 完成声明前各标注一次（双标注避免被遗漏）

**沉淀规则**：
- 节奏偏差 < 8h → §0 启动校验表单标注
- 节奏偏差 ≥ 8h → §0 启动校验表 + §6 完成声明前双标注
- 节奏偏差 ≥ 12h → 双标注 + 飞书通知（cron 调度异常）
