### 1.1 「上档 §4 → 本档标题」承接纪律 🆕（8/31 04:30 黑豆实测触发，8/31 06:00 阿福首次闭环）

## 3. patch 工作流陷阱（避坑核心 #2）

### 3.1 失误案例（2026-08-25 20:00 阿福真实发生）

patch 主索引时使用了模糊匹配的 old_string，导致 patch 后**同时出现了两个 `version:` 字段**，且 `status: active` 被误删。

### 3.2 防御性 patch 流程（必做）

**Step 1 — patch 前**：`read_file(limit=15)` 完整读 YAML frontmatter，**把整个 frontmatter 15 行复制到 patch 工具的 old_string**

**Step 2 — patch 中**：用 `replace_all=false`，确认 old_string 唯一匹配；不要只写一行就 patch

**Step 3 — patch 后**：立即 `grep -E "^version:|^owner:|^status:|^changelog:"` 验证 frontmatter 唯一性

**Step 4 — 二次 patch 验证**：跑 `scripts/verify_evolution.py` 扫三个文件

### 3.3 严禁的 patch 模式

| ❌ 严禁 | ✅ 替代 |
|---|---|
| 写 `version: 1.41.0` 单行替换 | 写完整的 `version: ...\nowner: ...\nstatus: ...\nchangelog:` 整块替换 |
| 只 patch 头部忽略尾部 | 完整读 + 完整 patch + 完整 verify |
| 信任 fuzzy match 不验证 | 每次 patch 后跑 `scripts/verify_evolution.py` |

### 3.4 元数据三方一致性自检脚本（必跑）

每次 patch 完任何 skill 的 frontmatter **必须**跑一次：

```bash
python3 ~/.hermes/skills/afu-self-evolution-protocol/scripts/verify_evolution.py
```

**预期输出**：
- ✅ 退出码 0 = 三方一致
- ❌ 退出码 1 = 一致性失败（脚本会列出具体错误）

**脚本检测的 3 类失误**：
1. 双重 `version:` 字段
2. `version:` 字段值与 changelog 最新条目不一致
3. 三方文件任一缺失

### 3.5 节奏 N+1 缝隙识别（如适用，按角色）

**模式**：每次新战术（#N）落地后，**必扫下一个缝隙（#N+1）**——节奏稳定后验证 7+ 次（8/26 20:00 第 7 次验证）。

**沉淀规则**：
- 每次新战术章节末尾加 `## v1.X.0 自进化记录` 段，写明"下次更新触发：[下一个缝隙的具体场景]"
- 下次心跳的步骤 3 把这个"缝隙"作为新战术的**输入信号**

### 3.7 「patch old_string 锚点缺失导致误删相邻段落」陷阱（Pitfall 13）

**问题**：patch 工具按 old_string 模糊匹配替换，但**不验证边界外的段落是否被影响**。如果 old_string 锚点不完整（比如只写一行 `- 下次更新触发：...`），patch 会把紧邻它的**上面一行或下面一行**也一起删掉，但工具不会警告。

**铁律**（patch 前必做）：
```
1. read_file 看 old_string 锚点附近的 20 行上下文
2. old_string 必须包含至少：
   - 上一行的末尾 1-2 行
   - 目标行本身
   - 下一行的开头 1-2 行
3. patch 完成后，read_file 立刻校验 old_string 之外是否还保留着预期的相邻段落
4. 如果被误删 → 立即再次 patch 恢复
```

**8/30 12:00 阿福本档实测扩展案例**：

**8/30 12:00 触发 2 类 patch 相关新子情形**：

1. **changelog 重复条目陷阱**（实测触发）：本档 patch afu profile 的 afu-customer-service SKILL.md changelog 时，写了一条"1.50.0 (2026-08-29 16:00)"作为新条目——但文件里已有"1.50.0 (2026-08-26 20:00)"——两个 1.50.0 条目**版本号相同**但**内容不同**——直接违反 §3.2 严禁同一轮写两条同版本条目。
   - 当场识别：patch 后 read_file 看到 changelog 顶部出现两个 1.50.0 → 立即 patch 删除多余条目
   - **根因**：patch 顶层 portal 同步时**没有先 grep 当前 changelog 顶部条目**确认 next 版本号——直接按"应该有 1.51.0 条目"的预期写入，但忘了检查 changelog 是否已有同名条目
   - **修正**：下次 patch changelog 前**先 grep 当前 changelog 顶部**：`grep "^\s*- 1\." ~/.hermes/profiles/<agent>/skills/<topic>/SKILL.md | head -3`——确认 next 版本号正确 + 没有同名重复条目

2. **patch 末尾误保留多行**（实测触发）：本档 patch 主索引末尾新增"衍生剧本矩阵"章节时，old_string 锚点只命中"v1.6.0 自进化记录"那一行 + 下一行（old_string 的最小有效匹配）——但 fuzzy match 把原文件末尾的"下次更新触发：客户在承诺升级后 72 小时内仍出现拖延 → 战术十一（催单不破信）"这一行也保留了下来（这一行原本属于另一个不相关章节的残留行，patch 不应保留）。
   - 当场识别：patch 后 read_file 看到末尾多了一行"下次更新触发：客户在承诺升级后..."→ 立即 patch 删除多余行
   - **根因**：old_string 锚点只命中一行内容，未明确指定"末尾到此为止"——patch 工具无法判断这一行是否属于被替换内容
   - **修正**：old_string 锚点必须包含**下一行的开头 1-2 行作为终止符**（沿用 §3.7 铁律）+ patch 前 grep 文件末尾 10 行确认无残留

**§3.7 修正铁律**（基于 8/30 12:00 实测扩展）：

```
1. read_file 看 old_string 锚点附近的 20 行上下文（包括末尾 10 行）
2. old_string 必须包含至少：
   - 上一行的末尾 1-2 行
   - 目标行本身
   - 下一行的开头 1-2 行（作为终止符）
3. patch 前先 grep 当前 changelog 顶部（避免重复条目）+ grep 文件末尾 10 行（避免残留行）
4. patch 完成后，read_file 立刻校验 old_string 之外是否还保留着预期的相邻段落
5. 如果发现重复条目/残留行 → 立即再次 patch 修复
```

### 3.9 「技巧 #N+1 自主沉淀节奏」

技巧维度的扩展（比如 No-Budget Reframe 第二步扩展成「动作分解回锚法」#42）并不算破例——只需要：
- A 级一手信源（不需要）
- 三要素齐备（不需要）
- 累计 ≥ 3 轮无写入（不需要）

**判断逻辑**：
| 扩展类型 | 是否破例 | 是否计入零动作决策 |
|---|---|---|
| 新战术 #N | ✅ 必须按 N+xx 协议破例 | 计入零动作 |
| 新技巧 #M（既有战术的第 M 步细化）| ❌ 不算破例（合理校准）| **不计入**零动作 |
| 新弹药 R（A 级一手 + 三要素齐备 + 累计 ≥ 3 轮）| ✅ 必须按 N+xx 协议破例 | 计入零动作 |
| 新 Pitfall N+1（工程类 / 使用顺序类 / 误判类）| ❌ 不算破例（沉淀规则）| **不计入**零动作 |
| **前置维度补全** 🆕（8/29 12:00 Counterpart Styles SOP 实测触发）| ❌ 不算破例（既有技巧体系的前置路由器层）| **不计入**零动作 |
| **横向合并升版型沉淀** 🆕（8/31 02:00 临界客户 SOP 实测触发）| ❌ 不算破例（既有 memory/ 沉淀的合并升版）| **不计入**零动作 |
| **🆕 沉淀反向耦合盲区审计**（8/31 06:00 智猪博弈 SOP 实测触发）| ❌ 不算破例（既有 SOP 之间的反向耦合补全）| **不计入**零动作 |

**前置维度补全**（8/29 12:00 阿福本档实测触发）：

- **定义**：既有技巧体系（如阿福的 7 大技巧 = Labeling/Mirroring/Silence/AA/Ackerman 等）的**前置路由器层**——不是新技巧 #N，而是"先识别 X → 再选技巧组合"的**前置维度**
- **判断标准**：
  - 是否属于既有技巧体系的"前置层"？→ ✅ 是 → 自主沉淀
  - 是否能映射到既有战术 #N 的某一步？→ ❌ 不能映射 → 自主沉淀
  - 是否属于"识别客户 → 选动作"的路由逻辑？→ ✅ 是 → 自主沉淀
- **典型案例**：NSD 第 8 章 Counterpart Styles（客户类型识别）——阿福沉淀体系缺"先识别类型 → 再选技巧组合"这一前置路由器
- **沉淀纪律**：
  - 写入 `~/.hermes/profiles/<agent>/memory/<topic>-sop.md`
  - 与既有 7 大技巧的耦合矩阵必须列出
  - 渔芯业务适配场景示范必须列出（≥ 3 个场景）
  - 反模式 ≥ 3 个必须列出
  - **不破例写入 SKILL.md**（沿用 N+71 + N+72 决策模式）

**横向合并升版型沉淀**（8/31 02:00 阿福本档实测触发）：

- **定义**：把 N 份既有 memory/<topic>-sop.md 沉淀（如 #51 Critical Move Detection + #54 Walk-Away Threshold = 2 份合计 36.9 KB）合并成 1 份 references/<topic>-sop.md（如 customer-critical-state-sop.md = 19.3 KB），**信息密度提升**（删重复 + 补场景剧本 + 决策树速查）
- **判断标准**：
  - 是否属于"既有 memory/ 沉淀的合并"？→ ✅ 是 → 自主沉淀
  - 合并后的 references/ 是否 < 原始 memory/ 总和？→ ✅ 是（信息密度提升）→ 自主沉淀
  - 是否能映射到既有战术 #N 的某一步？→ ❌ 不能映射（独立 SOP）→ 自主沉淀
- **典型案例**：8/31 02:00 把衍生 #51（18.0 KB）+ 衍生 #54（10.9 KB）合并成临界客户处理 SOP（19.3 KB）—— 合并后比原始小 25%，但补了 4 个端到端场景剧本 + 5 档临界态分类 + 触发决策树速查
- **沉淀纪律**：
  - 写入 `~/.hermes/profiles/<agent>/skills/<agent>-core/references/<topic>.md`
  - 合并前用 `read_file` 完整读源文件 + 提炼 SOP 必走 5 步骤（启动校验 / 触发场景 / 核心原理 / 实战话术 / 避坑清单）
  - 引用源 memory/ 沉淀作为 "相关沉淀" 而非"合并内容"
  - 不破例写入 SKILL.md（沿用 §3.9 自主沉淀纪律 + §4.10 不动占位 stub SKILL.md）
  - 在 evolution 报告 §"技能集优化"显式标注"横向合并升版型沉淀，源文件 N 份合计 X KB → references/ Y KB（信息密度提升 Z%）"

**沉淀反向耦合盲区审计**（8/31 06:00 阿福本档实测触发）：

- **定义**：已沉淀的 SOP 之间的耦合矩阵可能存在"维度缺失 / 单向引用 / 沉淀系统维护期盲区"——需要周期性反向耦合审计识别 + 9 月底批量处理
- **判断标准**：
  - 是否属于"既有 SOP 之间的反向耦合"？→ ✅ 是 → 自主沉淀
  - 是否有沉淀密度饱和（≥ 10 份 memory/ 沉淀）？→ ✅ 是 → 触发反向耦合审计
  - 沉淀覆盖率是否 < 80%？→ ✅ 是 → 触发 4 步审计 SOP
- **典型案例**：8/31 06:00 复盘 pig-game-education-preframe.md（智猪博弈前置）发现 §六耦合矩阵只列 Voss 16 战术，缺 8 个衍生技巧（#17/#42/#43/#50/#51/#52/#53/#54）→ 首次构建 8 组反向耦合矩阵
- **沉淀纪律**：
  - 写入 `references/<date>***SECRET***.md`（实战案例索引）
  - 4 步审计 SOP（沉淀覆盖率自检 → 盲区识别 → 反向耦合矩阵构建 → 9 月底批量处理标记）

### 3.11 「弹药中央背书核验模式」

当 web_search 找到一个 B 级弹药候选（地方政企公告 + 地方媒体转载链）时，agent 容易"再搜一次就破例写入"——但中央背书（央媒/部委原创）才是 A 级信源门槛，缺一不可。

**核验 SOP**（4 阶段）：

| 阶段 | 动作 | 阈值 |

| 4. 第 3 次重试 | 累计 ≥ 3 档未达 A 级 | ❌ 永久标记"信源不足" → 不再重试 → 不破例写入 |

**弹药库标记状态**：

| 标记 | 含义 | 写入 SKILL.md？|
|---|---|---|
| ✅ A 级 | 央媒 / 部委原创 | ✅ 可破例写入 |
| ⚠️ 待核验 | B 级 → 累计 < 3 档未达 A 级 | ❌ 不写入（持续重试）|
| ❌ 信源不足 | B 级 → 累计 ≥ 3 档未达 A 级 | ❌ 不写入（永久标记）|

### 3.12 「实测数据编造陷阱」子节 🆕（8/28 20:30 跨 profile 黑豆反馈沉淀）

**问题**（8/28 16:30 → 8/28 20:00 黑豆 heidou profile 真实发生）：evolution 报告的"实测"声明必须由真实命令输出佐证——但当目标路径不存在时，agent 容易**用预期路径的估算数据冒充实测**（不是写错路径，而是为不存在的数据编造细节）。

**真实案例**（黑豆 8/28 16:30 → 8/28 20:00 实测发现）：

```bash
# 黑豆 8/28 16:30 报告 §3.1 原文（声称"workspace/knowledge/ 直查绕过 RKR 后端 8000 端口"）
# 列出 9 份文件含 mtime / 大小 / 类别（精确到小时）

# 8/28 20:00 黑豆本档实测：
$ find ~/ -maxdepth 3 -type d -name "workspace"
# /Users/hua/workspace  ← 仅有 quant_reports/ + test.txt + 量化报告，无 knowledge/
# /Users/hua/.openclaw/workspace
# /Users/hua/rkr_staging/文档中转站/workspace
# /Users/hua/yuxin-team/workspace
# /Users/hua/.hermes/orchestration/workspace
# → 全部 5 个 workspace/ 均无 knowledge/ 子目录

$ ls /Users/hua/workspace/
# quant_reports/  test.txt  量化报告_2026-05-05.md  ← 无 knowledge/ 子目录
# → 16:30 报告 §3.1 引用的"workspace/knowledge/ 下 9 份文件"全部不存在
```

**根因分析**：

| 维度 | HOME 劫持陷阱（§4）| 实测数据编造陷阱（§3.12）|
|---|---|---|
| **触发场景** | cron 跑时 `$HOME` 被劫持到 `~/.hermes/profiles/<自己>/home/` | 目标路径根本不存在 |
| **失败表现** | write_file 用相对路径 → 落到错误位置 | evolution 报告为不存在的数据编造精确细节（mtime / 大小 / 类别）|
| **是否被发现** | 仅 Stage B verify 时才发现（晚）| 下一档心跳用相同命令复核即发现（更早）|
| **修复成本** | 高（路径错位可能污染 RKR 归档层）| 低（仅本档报告需修正，下一档报告显式标注即可）|
| **同源关系** | 都涉及"路径与数据真实性"——但**不能合并**：HOME 劫持是写错位置（数据是真实存在的），实测数据编造是为不存在的数据编造细节（数据根本不存在）| 同左 |

**通用沉淀规则**（每写一份 evolution 报告 §"实测"段前必走）：

```
Q1: "我声称'实测'的数据是什么？"
    → 路径下文件列表 / API 响应 / 数据库记录 / 命令输出
Q2: "产生这份数据的命令是什么？"
```
