# 自我进化 cron 工作流协议（跨 profile 类级）

> **本 skill 的存在理由**：从 8/25 开始，阿福每 4 小时跑一次 cron 自我进化轮，期间反复出现 3+ 类本可避免的失误。**8/28 20:30 升级为跨 profile 类级协议**——黑豆 heidou profile 在 8/28 16:30 evolution 报告 §3.1 落入"实测数据编造陷阱"（引用了不存在的 `workspace/knowledge/` 下 9 份文件 mtime 表），证明**所有跑 self-evolution cron 的 agent 都可能落入此陷阱**，不仅是阿福。
> **核心原则**：evolution 报告**任何"实测"声明**都必须有命令原始输出佐证；路径不存在时**严禁编造细节**——必须降级为"默认决策框架"或"沿用上期"。

---

## 1. 自我进化 5 步骤（强制顺序）

| 步骤 | 动作 | 工具 | 强制项 |
|---|---|---|---|
| 1 | 心跳检查 | `python3 ~/.hermes/scripts/heartbeat_check.py <agent>` | ✅ 必做 |
| 2 | 复盘最近 3 次 evolution 报告 | `ls -t ~/.hermes/profiles/<agent>/evolution/ \| head -3` + 读文件 | ✅ 必做 |
| 3 | 学习 1 个新技巧/战术/政策 | web_search / skill_view / 已有 skill 实践缝隙 | ✅ 必做 |
| 4 | 阅读行业最新资讯（如适用）| web_search + 已有行业 skill | 🟡 按角色适用 |
| 5 | 优化技能集 + 输出进化报告 | patch + write_file + 元数据三方一致 | ✅ 必做 |

**严禁跳过任何一步**——即使步骤 1 心跳静默无任务，也要走完 2/3/4/5。

## 2. 元数据三方一致纪律（最重要的纪律）

### 2.1 三个文件必须同时升级（如适用）

| 文件 | 路径 | 角色 |
|---|---|---|
| **内容本体** | `~/.hermes/profiles/<agent>/skills/<topic>/SKILL.md` | 内容层（详） |
| **顶层门户** | `~/.hermes/profiles/<agent>/skills/<agent>-core/SKILL.md` | 顶层入口（轻） |
| **主索引** | `~/.hermes/skills/<agent>-<topic>/SKILL.md` 或 skills/<category>/<topic>/SKILL.md | 主索引（最全） |

> **跨 profile 类级说明**：每个 profile（阿福、黑豆、玉芬等）的三方对应关系不同；本协议不绑定具体三方对应关系，只规定"必须三方都 ≥ 上轮版本 + changelog 最新条目对得上"。

### 2.2 changelog 写入纪律（避坑核心 #1）

- ❌ **严禁同一轮写两条 changelog 条目**（如同时写 1.42.0 + 1.43.0）
- ✅ 每轮只追加 1 条 changelog
- ✅ changelog 顺序：**最新在上**——patch 工具默认追加到末尾，但 SKILL.md 的 changelog 阅读约定是"最新在上"

### 2.3 6 文件级联升级模式（8/26 04:00 实测稳定）

当新战术/技巧同时引发"使用顺序 pitfall"和"实战启动参考文档"时，**单期需级联升级 6 个文件**：

| # | 文件 | 何时升级 |

| 1 | 内容本体 SKILL.md | 战术章节 + 自进化记录 + 顶端 changelog/version/tags |
| 2 | 顶层门户 SKILL.md | 顶端 changelog + "主索引当前版本" 字段 +1 |
| 3 | 主索引 SKILL.md | 顶端 changelog + version +1 |

**顺序原则**：先 patch 内容本体（1）→ 再 patch 顶层门户（2）→ 再 patch 主索引（3）→ 再加 pitfall（4）→ 最后新建 2 个 references（5/6）。

## 3. patch 工作流陷阱（避坑核心 #2）

### 3.1 失误案例（2026-08-25 20:00 阿福真实发生）

patch 主索引时使用了模糊匹配的 old_string，导致 patch 后**同时出现了两个 `version:` 字段**，且 `status: active` 被误删。

### 3.2 防御性 patch 流程（必做）

**Step 1 — patch 前**：`read_file(limit=15)` 完整读 YAML frontmatter，**把整个 frontmatter 15 行复制到 patch 工具的 old_string**

**Step 2 — patch 中**：用 `replace_all=false`，确认 old_string 唯一匹配；不要只写一行就 patch

**Step 3 — patch 后**：立即 `grep -E "^version:|^owner:|^status:|^changelog:"` 验证 frontmatter 唯一性

**Step 4 — 二次 patch 验证**：跑 `scripts/verify_evolution.py` 扫三个文件

### 3.3 严禁的 patch 模式

| ❌ 严禁 | ✅ 替代 |
|---|---|
| 写 `version: 1.41.0` 单行替换 | 写完整的 `version: ...\nowner: ...\nstatus: ...\nchangelog:` 整块替换 |
| 只 patch 头部忽略尾部 | 完整读 + 完整 patch + 完整 verify |
| 信任 fuzzy match 不验证 | 每次 patch 后跑 `scripts/verify_evolution.py` |

### 3.4 元数据三方一致性自检脚本（必跑）

每次 patch 完任何 skill 的 frontmatter **必须**跑一次：

```bash
python3 ~/.hermes/skills/afu-self-evolution-protocol/scripts/verify_evolution.py
```

**预期输出**：
- ✅ 退出码 0 = 三方一致
- ❌ 退出码 1 = 一致性失败（脚本会列出具体错误）

**脚本检测的 3 类失误**：
1. 双重 `version:` 字段
2. `version:` 字段值与 changelog 最新条目不一致
3. 三方文件任一缺失

### 3.5 节奏 N+1 缝隙识别（如适用，按角色）

**模式**：每次新战术（#N）落地后，**必扫下一个缝隙（#N+1）**——节奏稳定后验证 7+ 次（8/26 20:00 第 7 次验证）。

**沉淀规则**：
- 每次新战术章节末尾加 `## v1.X.0 自进化记录` 段，写明"下次更新触发：[下一个缝隙的具体场景]"
- 下次心跳的步骤 3 把这个"缝隙"作为新战术的**输入信号**

### 3.6 「战术使用顺序」与「战术误判」类 pitfall

| Pitfall | 类别 | 案例 |
|---|---|---|
| 1-8 | 工程类 | changelog 顺序 / patch 双重 version / fuzzy match / HOME 劫持等 |
| 9 | **战术使用顺序类** | 战术十二 Pre-mortem 在战术十之前使用 → 客户觉得"他在唱衰" |
| 10 | **战术使用顺序类** | 战术十三 Hard Date 时间锚定过远（>10 天）→ 客户大脑丢失感知 |
| 11 | **战术使用顺序类** | 战术十四连环失守未升级 |
| 12 | **战术误判类** | 战术十五误判决策疲劳为冷淡——决策疲劳 ≠ 冷淡 |
| 13 | **工程类** | patch old_string 锚点缺失导致误删相邻段落（详见 §3.7）|
| 14 | **战术误判类** | 战术十六误判摩擦峰值为决策疲劳复发——摩擦峰值 ≠ 决策疲劳复发 |
| 15 | **技巧误判类** | 技巧 #42 动作分解回锚法在报价前使用 → 客户大脑被一整块报价单砸晕 |

**Pitfall 12 + 14 + 15 + 16 同构**：
- 12/14/15：都是"两个客户状态处理方向完全相反"的误判陷阱
- 16：是"实测声明 vs 路径不存在"的编造陷阱
- 共同点：误判 = 帮倒忙（pitfall 12/14/15）/ 误判 = 误报告下游决策（pitfall 16）

### 3.7 「patch old_string 锚点缺失导致误删相邻段落」陷阱（Pitfall 13）

**问题**：patch 工具按 old_string 模糊匹配替换，但**不验证边界外的段落是否被影响**。如果 old_string 锚点不完整（比如只写一行 `- 下次更新触发：...`），patch 会把紧邻它的**上面一行或下面一行**也一起删掉，但工具不会警告。

**铁律**（patch 前必做）：
```
1. read_file 看 old_string 锚点附近的 20 行上下文
2. old_string 必须包含至少：
   - 上一行的末尾 1-2 行
   - 目标行本身
   - 下一行的开头 1-2 行
3. patch 完成后，read_file 立刻校验 old_string 之外是否还保留着预期的相邻段落
4. 如果被误删 → 立即再次 patch 恢复
```

### 3.8 「误判陷阱类 pitfall」通用沉淀规则

每加 1 战术必问 Q1-Q4——如果 Q4 答案是"完全相反"，就必须新增 Pitfall N（误判类）+ 同步更新 pitfalls 文件。

### 3.9 「技巧 #N+1 自主沉淀节奏」

技巧维度的扩展（比如 No-Budget Reframe 第二步扩展成「动作分解回锚法」#42）并不算破例——只需要：
- A 级一手信源（不需要）
- 三要素齐备（不需要）
- 累计 ≥ 3 轮无写入（不需要）

**判断逻辑**：
| 扩展类型 | 是否破例 | 是否计入零动作决策 |
|---|---|---|
| 新战术 #N | ✅ 必须按 N+xx 协议破例 | 计入零动作 |
| 新技巧 #M（既有战术的第 M 步细化）| ❌ 不算破例（合理校准）| **不计入**零动作 |
| 新弹药 R（A 级一手 + 三要素齐备 + 累计 ≥ 3 轮）| ✅ 必须按 N+xx 协议破例 | 计入零动作 |
| 新 Pitfall N+1（工程类 / 使用顺序类 / 误判类）| ❌ 不算破例（沉淀规则）| **不计入**零动作 |
| **前置维度补全** 🆕（8/29 12:00 Counterpart Styles SOP 实测触发）| ❌ 不算破例（既有技巧体系的前置路由器层）| **不计入**零动作 |

**前置维度补全**（8/29 12:00 阿福本档实测触发）：

**根因分析**：

|---|---|---|

**通用沉淀规则**（每写一份 evolution 报告 §"实测"段前必走）：

```

Q4: "如果 Q3 命令的输出为空或路径不存在，下一份报告如何标注？"
    → 必须显式标注"路径不存在，本 cron 无实测" + 不引用预期估算
```

**沉淀规则**：

- evolution 报告**任何"实测"声明**必须附命令原始输出（或引用 evolution/YYYY-MM-DD_HH.md §X 段）

## 4. HOME 劫持防御（避坑核心 #3）

### 4.1 现象

每次 cron 跑 `python3 ~/.hermes/scripts/heartbeat_check.py <agent>` 时，`$HOME` 会被劫持到 `~/.hermes/profiles/<agent>/home/`。如果用相对路径或 `Path.home()` 写资料，会落到错误位置。

### 4.2 必做 30 秒自检（进化轮第一步）

```bash
# 1. 看 $HOME
echo "HOME=$HOME"
# ✅ 应该是: HOME=/Users/hua
# ❌ 如果是: HOME=/Users/hua/.hermes/profiles/<agent>/home/, 必须修复

# 2. 修复
export HOME=/Users/hua

# 3. 复检 — 修一次不算，必须 echo 再看一次
echo "HOME=$HOME"   # ✅ 必须显示 /Users/hua 才算修复完成

# 4. 所有写操作使用绝对路径
# ✅: write_file(path="/Users/hua/.hermes/profiles/<agent>/evolution/...")
# ❌: write_file(path="~/.hermes/profiles/<agent>/evolution/...")
```

### 4.3 复检纪律（避坑强化）

**铁律**：
- ✅ `export HOME=/Users/hua` 之后**立即** `echo "HOME=$HOME"` 复检
- ✅ 显示 `/Users/hua` → 继续
- ❌ 任何其他值 → 停下来排查（export 是否生效？profile 是否嵌套？）

### 4.4 「实测数据 vs 预期估算红线」子节 🆕（8/28 20:30 跨 profile 黑豆反馈沉淀）

**问题**（8/28 16:30 → 8/28 20:00 黑豆 heidou profile 真实发生）：§4.1-4.3 只防御"路径错位"（HOME 劫持 → write_file 写到错误位置），但**未防御"路径不存在时编造数据"**——后者是 evolution 报告独有的陷阱（write_file 不会因路径不存在而报错，但 evolution 报告中的"实测数据"必须真实）。

**红线规则**（与 §3.12 Pitfall 16 配套，但视角不同：§3.12 关注**怎么发现**，§4.4 关注**怎么避免**）：

| 红线 | 含义 | 违反后果 |
|---|---|---|
| **红线 1** | evolution 报告任何"实测"声明必须有命令原始输出佐证 | 误判进入下游决策（如 §3.6 Pitfall 16 真实案例）|
| **红线 2** | 命令输出为空或路径不存在时**严禁编造细节**——必须降级为"默认决策框架"或"沿用上期" | 后续 cron 报告继承误判，进入恶性循环 |
| **红线 3** | staging_save.py 调用历史 / 已知 mtime 估算值**严禁冒充实测数据** | 与 §4.1 HOME 劫持同源（路径与数据真实性）——但表现不同 |
| **红线 4** | 下一档心跳若发现上档"实测"声明有误，必须在本档报告 §0 显式标注"上期 §X 误判修正" | 否则误判持续沉淀 |

**与 §4.1-4.3 HOME 劫持防御的关系**：

- §4.1-4.3 防的是"**写错位置**"（HOME 错 → write_file 写到错路径）
- §4.4 防的是"**编造不存在的数据**"（路径不存在 → evolution 报告里为不存在的文件编造 mtime/大小）
- 两者**不可合并**——写错位置有 Stage B verify 兜底（晚但能发现），编造不存在的数据没有兜底（除非下一档心跳复核命令）

**为什么 §4.4 必须独立列出**：

- §4.1-4.3 是**写操作前**的自检（export HOME + echo 复检）
- §4.4 是**写报告前**的自检（声明"实测"前必贴命令原始输出）
- 两类自检时点不同、防御对象不同、违反后果不同——需要独立章节

### 6.1 「节奏缺位诚实标注模板」

**何时触发本模板**：
- 当前档与上档间隔 > 标准节奏（如 4h）的偏差
- 当前档与上档间隔 < 标准节奏（节奏被压缩）
- 当前档之间有 ≥ 1 档缺位

**诚实标注模板**（强制字段）：

```markdown
> 📌 **诚实自检·节奏**：本档与上档间隔 Xh（不是标准 4h 节奏）——根因：[具体原因——cron 调度问题 / 手动跳过 / 系统故障等]
> **N+xx 主动演练触发线**：[日期]（本档后 Yh）——本档已自然覆盖其"前/后 Yh 校准窗口" / 或 未覆盖
> **不构成节奏违规**：[判定条件] / 或 **构成节奏违规**：[理由]
```

**判定条件**：
- **不构成节奏违规**：
  - N+xx 主动演练触发线前的校准窗口已自然覆盖
  - 节奏偏差 < 2 个标准节奏（即 < 8h 间隔）
  - 本档核心动作仍按 §1 5 步骤完整执行
- **构成节奏违规**：
  - 节奏偏差 ≥ 2 个标准节奏（即 ≥ 8h 间隔且 N+xx 校准窗口未覆盖）
  - 本档跳过了 §1 任意步骤
  - N+xx 校准窗口未覆盖且本期无补救动作

**报告位置**：§0 启动校验表 + §6 完成声明前各标注一次（双标注避免被遗漏）

**沉淀规则**：
- 节奏偏差 < 8h → §0 启动校验表单标注
- 节奏偏差 ≥ 8h → §0 启动校验表 + §6 完成声明前双标注
- 节奏偏差 ≥ 12h → 双标注 + 飞书通知（cron 调度异常）
